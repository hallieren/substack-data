## pico's final report

The fix is a single-line change in `sympy/solvers/simplex.py` inside `linprog`.

## Problem

When `linprog` is called without `A` and `b` (no inequality constraints), it built the "empty" constraint system as:

```python
A, b = zeros(0, C.cols), zeros(C.cols, 1)
```

`A` has 0 rows (correct for "no constraints"), but `b` was incorrectly given `C.cols` rows of zeros. When this malformed pair reached `_simplex`, the internal consistency check saw `A` empty but `B` non-empty and raised the misleading `ValueError("must give A and B")` instead of solving / reporting the LP is unbounded.

## Fix

Changed the placeholder right-hand side to have zero rows, matching the zero-row constraint matrix:

```python
A, b = zeros(0, C.cols), zeros(0, 1)
```

Now a call like `linprog([-1])` represents a true unconstrained (except for implicit nonnegativity) LP and `_simplex` correctly raises `UnboundedLPError`.

This also fixes the related latent bug where calling `linprog` with only equality constraints (no `A`/`b`) previously crashed with a dimension mismatch when stacking equalities onto the empty `b`.

## Verification

- `linprog([-1])` now raises `UnboundedLPError` (the case from the PR description).
- `linprog([1])` returns `(0, [0])`, `linprog([2, 3])` returns `(0, [0, 0])`.
- `linprog([1], A_eq=[[1]], b_eq=[2])` returns `(2, [2])` (equality-only path works).
- Existing bounds cases (`linprog([1], bounds=(2, 3))`, `linprog([1], [], [], bounds=(2, 3))`) still work.
- Full existing simplex test suite passes (`6 passed`).

The final diff touches only the one source line and no tests/config.
